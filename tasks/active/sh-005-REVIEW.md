## Blocking findings

- **F1: `pixi.lock` records the editable self-install at the absolute path
  `/workspace`, so the lock is machine-specific** (`pixi.lock:316`,
  `pixi.lock:603`, `pixi.lock:9271`): all three references to the local
  package are the literal string `/workspace`, not a repo-relative path,
  even though `pixi.toml:32` declares `shelving-workbench = { path = ".",
  editable = true }`. That manifest/lock mismatch is the evidence; the
  installed dist agrees
  (`.pixi/envs/default/lib/python3.12/site-packages/shelving_workbench-0.0.1.dist-info/direct_url.json`
  is `{"url":"file:///workspace",...}`).

  Consequence: `.github/workflows/ci.yml:71-77` sets up pixi with
  `frozen: true` and then runs `pixi run full`. A frozen install replays the
  lock without re-solving, so on a GitHub runner (checkout under
  `/home/runner/work/...`) the `- pypi: /workspace` entry names a path that
  does not exist. The same applies to any contributor whose clone is not at
  `/workspace`. `pixi.lock` therefore does not satisfy the Must Have
  "`pixi.lock` is regenerated by `pixi install` and still resolves for
  `linux-64` and `linux-aarch64`" in any portable sense; it resolves only on
  this VM.

  This is stated as a hypothesis with the evidence above rather than a
  reproduction: confirming it by hand would mean re-rooting the checkout
  elsewhere, which is exactly the kind of untracked one-off this review
  should not rely on. Prove or disprove it in the next round. If pixi 0.78
  can be made to write a repo-relative path (a different manifest form, or
  regenerating the lock from a clean state rather than from whatever
  absolute-path `pixi add` produced it), do that. If pixi 0.78 always writes
  an absolute path for a `[pypi-dependencies]` path entry, then this
  approach to the editable self-install is incompatible with the repo's
  `frozen: true` CI and the task needs a different mechanism or an explicit
  decision recorded in the task file.

  Whichever way it lands, the guard belongs in the harness rather than in a
  reviewer's memory: a fast-tier check that `pixi.lock` contains no
  absolute filesystem path would catch a regression on the next
  `pixi install` by anyone. (The stronger check — that the lock installs
  from a checkout at a different path — is live-infrastructure-shaped and
  belongs in the full tier's harness per `pipeline.md` § Verification
  commands, not as a shell command run once during review.)

- **F2: the new exit-3 path has no committed test** (`test.sh:55-83`):
  `preflight_dev_extra` adds a second meaning to exit code 3 and an exact
  operator-facing message, and nothing exercises it.
  `tests/test_harness_cli.py` exists for precisely this contract — its
  module docstring says `test.sh`'s exit codes "are load-bearing, so they
  get real coverage here instead of being re-derived by hand each review
  round" — and it is byte-identical to `main` on this branch (4 test
  functions before and after). Execution Plan Step 6 discharged this as a
  manual simulation ("Simulate a stale env ... and confirm the preflight
  exits 3 naming it"), which leaves no trace: nothing in the repo tells a
  future author, human or agent, to re-run it, and I cannot confirm from
  the diff or either tier's output that the branch was ever taken.

  Add real coverage. Two workable shapes:
  1. Extract the check into a typed helper (`tools/check_dev_extra.py`,
     `mypy --strict`-clean per the standing Typed Python obligation, which
     `## Frontier Advice` already anticipates as an option), have
     `preflight_dev_extra` invoke it, and unit-test the name-extraction and
     missing-distribution logic directly, including the exact message and
     exit status.
  2. Keep the heredoc and add a `tests/test_harness_cli.py` case that runs
     `test.sh --fast` under a doctored `PATH`, following the recursion-safety
     rules that file's docstring already sets out (`preflight_dev_extra`
     runs first inside `run_fast`, so the run aborts before `pytest` is
     re-entered).

  Either way the assertion must pin the message text
  (`dev environment is out of sync with the [dev] extra: <names>. Run
  tools/install-deps.sh.`) and the exit status 3.

## Non-blocking notes

- **N1: `python3` is not in the tier's tool preflight** (`test.sh:56`,
  `test.sh:103`, `test.sh:109`): `preflight_dev_extra` shells out to
  `python3`, but the `preflight` tool lists name only `ruff mypy pytest
  rsync` (plus the full tier's extras). On a host without `python3` the
  harness dies with a bare 127 rather than the named-tool message and exit
  3 that `preflight` exists to produce. Adding `python3` to both lists is a
  one-line fix; fold it into whichever round addresses the blocking
  findings.
- **N2: the requirement-name regex misses a direct reference without
  surrounding whitespace** (`test.sh:69`): `re.split(r"[<>=!~;\[\s]", ...)`
  leaves `pkg@https://...` intact as the "name", so it would be reported
  missing forever. Today's `dev` extra is four bare names so nothing is
  wrong now; adding `@` to the character class costs nothing and removes a
  trap for whoever pins a direct reference later.
